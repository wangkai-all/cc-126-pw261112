# 分片迁移工作台

客户与订单按同一个客户标识路由到多个本地分片；支持版本化路由、在线扩容、可中断续传的复制、逐单元核验与原子切换。分片是独立的 SQLite 文件，不依赖任何外部集群，后端仅用 Python 标准库。

```bash
python3 -m app.server --port 8765          # 打开 http://127.0.0.1:8765
python3 -m unittest discover -s tests -v   # 13 个端到端用例
```

数据默认写入 `data/`（`shard-0.sqlite3`、`shard-1.sqlite3` …），可用 `--data DIR` 或环境变量 `SHARD_DATA` 指定。首次启动自动生成 18 位客户 / 54 笔订单；页面右上角「重建演示数据」可恢复初始状态。

## 核心设计

### 1. 同键路由与固定哈希

客户和订单只用一个路由键：`customer_id`。位置由固定算法决定，不随进程、节点或时间变化：

```
shard = fnv1a64(customer_id) % shard_count
```

`fnv1a64` 是 FNV-1a 64 位哈希，实现见 `app/router.py`。哈希本身不含分片数，**版本表**负责把 `version → shard_count` 固定下来（v1=2、v2=3 …）。因此同一位客户的全部订单永远和客户行落在同一分片，不会出现"客户在 A、订单散到 B/C"。

### 2. 版本化路由 + 绑定表（唯一的写入归属来源）

哈希只用来**算计划**，实际读写一律走控制分片上的 `bindings` 表：

| 字段 | 含义 |
| --- | --- |
| `customer_id` | 主键 |
| `shard` | 当前所有者分片 |
| `version` | 当前路由版本 |
| `generation` | 每次交接 +1，便于排查旧代读取 |
| `previous_shard` / `handoff_at` | 上一次交接的来源与时刻 |

扩容时，若某客户在新版本下的哈希位置变化，就要搬迁；位置不变的客户保持原分片，只在新版本正式 live 后原地升级绑定版本。页面「扩容切换计划」列出逐客户结论：当前绑定、v旧哈希、v新哈希、是否搬迁。

路由版本有三种状态：`live`（唯一对外）、`staging`（迁移中）、`retired`（已退役）。**旧版本只有在所有迁移单元都完成切换后才退役**；只要有单元冲突或未切换，旧版本保持 live，查询继续以绑定表为准。

### 3. 伪装的陷阱：为什么不能直接按哈希读

迁移中的客户，数据同时存在于源分片（仍是所有者）和目标分片（暂存副本）。如果查询直接按哈希落点读，会在切换前漏掉最新写入、切换后读到旧副本。"查一位客户"里保留「按版本哈希直读」只是**诊断视图**，用来直观看到"路由说去哪"和"数据实际在哪"的差异；页面实际结果始终来自所有者绑定。

### 4. 每个单元：复制 → 核验 → 原子切换

每个需要搬迁的客户是一个**迁移单元**，状态机：

```
planned → copying → copied → verified → switched → (cleaned)
              ↓ 中断
         interrupted ──续传──→ copying
              ↓ 内容不符
           conflict（停止，人工处理）
```

**复制**写入目标分片的 `migration_copy` 暂存表，主键 `(migration_id, customer_id, kind, row_key)`，天然幂等：

- 相同的复制请求重复执行只补缺失行，不重复写；
- 已存在的暂存行与源内容不同时不覆盖，而是把两侧原文写入 `unit_conflicts` 并停止该单元（见下）；
- `copy_seq` 记录已确认位置，中断后从暂存表继续，不从头再来。

**核验**在客户级锁内进行：

1. 先做增量对账——把复制开始后写入源分片的新订单补进暂存（迁移期间写入仍归源分片，见第 5 节）；
2. 逐行比较源快照与暂存副本：客户行数、订单行数、缺失/多余/内容不同行；
3. 计算 SHA-256 内容指纹（订单按 `created_at, order_id` 规范排序后序列化），两者必须一致；
4. 任一不符：记录 `unit_checks` 和 `unit_conflicts`（含源、暂存两份原文），单元置为 `conflict` 并停止，**不切换、不覆盖**。

**切换**分两步，都在同一把客户锁内：

1. 在目标分片物化该客户（只删/插这一位客户的行），此时绑定仍指向源；
2. 在控制分片的一个事务里同时更新 `bindings`（`shard=target, version=new, generation+1, previous_shard, handoff_at`）和 `migration_units.status=switched`。

这是一个原子所有权翻转：交接时刻之前写入只进源分片，之后只进目标分片；任何时刻只有一位所有者，查询不会同时读到两份。切换后再做一次目标分片与已核验暂存的比对，并写入 `unit_checks(phase='post_switch')`。

**清理**只对已切换单元开放；先确认绑定确实指向目标，再删除源分片上的旧副本，并做一次目标未受影响的核对。重复清理是空操作。

### 5. 迁移期间的写入归属与切换时机

| 阶段 | 写入去向 | 查询读取 |
| --- | --- | --- |
| planned / copying / interrupted / copied / verified | 源分片（绑定仍指向源） | 源分片 |
| 原子切换之后 | 目标分片 | 目标分片 |

新订单在复制中断、补写、续传、核验、切换各阶段都可以写入。核验前的增量对账会把复制期间落到源分片的新订单补进暂存；因此切换后目标分片包含全部订单，源分片上的"迟到"副本在清理前作为证据保留，但不参与路由。

### 6. 端到端一致性

`Engine.audit()`（页面「运行一致性与审计」）逐客户检查：

- 每条绑定都指向确实存在客户行的分片；
- 所有者分片有该客户的订单；
- 没有孤儿订单（`orders.customer_id` 无对应客户行）；
- 非所有者分片上的保留副本内容与所有者一致（否则报告冲突）。

## 页面演练剧本

1. **中断 → 补写 → 续传**：规划迁移后，对某单元只复制 1 行即中断；补写一笔订单（仍进源分片）；续传补完；核验并切换；再补写一笔（进目标分片）；用「切换前后三视图对照」查看所有者、v旧/v新哈希直读与物理副本。
2. **冲突 → 停止并留证**：复制 2 行后注入冲突（修改源端已暂存订单的金额与备注）；续传时发现暂存与源不一致，单元停止，冲突面板展示两侧逐字段差异；此时该客户仍路由到源分片，旧版本保持 live。
3. **切换前后对照**：对任一单元查看所有者绑定、各版本哈希落点、物理存在情况。
4. **运行全部单元**：全部切换后 v2 变 live、v1 退役；「清理全部旧副本」删除各源分片上的保留数据。

## 代码结构

| 文件 | 职责 |
| --- | --- |
| `app/router.py` | FNV-1a 哈希、`shard_for`、版本表、搬迁计划 |
| `app/store.py` | SQLite 分片存储：schema、事务、快照、暂存行、内容指纹 |
| `app/engine.py` | 迁移引擎：规划、复制/续传、核验、切换、清理、冲突留证、审计 |
| `app/server.py` | 标准库 HTTP 服务 + JSON API + 静态文件 |
| `app/static/` | 单页工作台（原生 HTML/CSS/JS，无构建步骤） |
| `tests/test_migration.py` | 端到端用例：路由、幂等、中断续传、切换、冲突、版本生命周期、清理、审计 |

## 不变量（测试覆盖）

- 同一客户及订单共享一个路由键与所有者分片。
- 相同迁移请求重复执行复用原计划，不重复复制；重复复制/清理是空操作。
- 中断后从已确认位置续传，暂存行不重复。
- 切换前后写入分别落到源/目标分片，查询结果不丢不重。
- 内容冲突时保留两侧证据、停止该单元，不用最后写入覆盖。
- 旧路由版本在所有单元切换前不退役。
- 清理只删已切换单元的旧副本，不影响所有者数据。
